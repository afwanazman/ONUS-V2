A locally-hosted, air-gapped assessment tool. Point it at a target you are
authorized to test and it runs 8 scanning modules in parallel, deterministically
scores every finding (CVSS v3.1), optionally adds AI-generated plain-English
descriptions via a local LLM, and produces a PDF report plus a live web
dashboard. No external API calls - everything runs on your own network.

**What this fork is for:** growing ONUS from a VAPT scanner into a single
console for the checks a small team runs before shipping - starting with
*"is it safe?"* (upstream's scanning pipeline) and adding *"does it hold
up?"* (k6 load testing). Both run through the same queue, the same job
model, and the same report surface, so one operator gets one place to look
instead of two tools and two dashboards.

That's the direction, not a finished claim. Today the fork ships exactly one
new pipeline; the rest of the roadmap is below and honestly labelled as such.

## What's different from upstream

Everything in this section is new in ONUS-V2. Everything *not* in this section
is upstream's work, unchanged.

### 1. Load testing pipeline (k6)

A second, independent job type that lives alongside the VAPT scan. Drive real
traffic at an endpoint, find where it degrades, and get the numbers plus a
plain-English read on them.

| | |
|---|---|
| **Engine** | [Grafana k6](https://k6.io) v0.54.0, pinned as a single Go binary in `backend/Dockerfile` |
| **Scenarios** | Ramp up/down, Constant load, Spike, Soak, Stress |
| **Shape** | 1-1000 virtual users, 5s-1h duration, any HTTP method, custom headers, request body |
| **Auth** | Same pre-flight login flow as an authenticated scan (auto-detect / HTML form / JSON API) |
| **Thresholds** | Optional p95 latency budget and max error rate; a run that exceeds either is reported as failed |
| **Metrics** | avg/min/max and p50/p90/p95/p99 latency, req/s, error rate, total requests, data in/out, VUs, iterations - plus a per-second timeseries for live charting |
| **Analysis** | Deterministic first: breaking-point detection (the VU count where p95 latency doubles off baseline or errors pass 5%) and a 0-100 performance score. AI prose second, and only on top |

The AI layer follows upstream's own rule, deliberately: **numbers are never
generated by the LLM.** `analysis/load_analyzer.py` computes the score and the
breaking point deterministically, exactly the way `analysis/cvss_scorer.py`
computes severity for scan findings; Ollama only turns the finished numbers into
an executive summary and a recommendation list. The measurements themselves
obviously vary run to run - that's what measuring a live system means - but the
score and breaking point derived *from* a given set of measurements are a pure
function of them, and the LLM never touches either.

**Where the code lives:**

| Path | Role |
|---|---|
| [`backend/tasks/k6_runner.py`](backend/tasks/k6_runner.py) | Generates the k6 JS scenario from the job config, runs it under a scaled subprocess timeout, parses the JSON summary |
| [`backend/tasks/loadtest_orchestrator.py`](backend/tasks/loadtest_orchestrator.py) | Top-level Celery task: k6 → analyse → AI prose → DB. Mirrors `scan_orchestrator.py`, minus the multi-module chord and the operator-decision pause |
| [`backend/analysis/load_analyzer.py`](backend/analysis/load_analyzer.py) | Breaking-point detection, performance score, severity brackets, AI summary hand-off |
| [`backend/routers/loadtest.py`](backend/routers/loadtest.py) | `POST /api/loadtest`, `GET /api/loadtest/{id}/status`, `GET /api/loadtest/{id}/results`, `POST /api/loadtest/{id}/cancel`, `GET /api/loadtest/scenarios` |
| [`backend/models.py`](backend/models.py) | `LoadTest` table (migration `f5c7d8e1a934_add_load_tests_table`) |
| [`frontend/components/loadtest-form.tsx`](frontend/components/loadtest-form.tsx) | `/loadtest/new` - the configuration form |
| [`frontend/components/loadtest-results.tsx`](frontend/components/loadtest-results.tsx) | `/loadtest/[id]/status` - live progress and results |

### 2. Load-test UI, rebuilt on upstream's design system

The first cut of the load-test form was functionally complete but visually its
own thing - eight stacked cards, uppercase labels, a native checkbox, off-palette
red error states. It has been rebuilt to sit inside upstream's "printed field
manual" system rather than beside it:

- one 640px form sheet, matching the New Scan page, instead of a column of cards
- upstream's token palette throughout (`crit` / `authz` / `accent`), no raw
  Tailwind colours
- the authorization confirmation uses the same amber `authz` affordance the scan
  form reserves for legal/policy consent - fitting, since a load test generates
  real traffic
- live URL validation with the same check/cross indicator as the domain field
- `MagneticButton` submit, `Panel` surfaces, `Plate` margin decor, staggered
  `onus-fade-up` entrances - all existing primitives, nothing new invented
- a dial instrument in the hero whose needle tracks the configured VU count,
  answering the scan page's target reticle

### 3. Job deletion

Upstream has no delete: `routers/scan.py` exposed only `POST` and `GET`, and the
Scans ledger's checkboxes selected rows that nothing could then act on. This fork
adds deletion end-to-end.

| | |
|---|---|
| **Endpoints** | `DELETE /api/scan/{id}` (204) and `POST /api/scans/delete` for the ledger's bulk action |
| **Scope** | Both route through `get_owned_scan_or_404`, so hosted mode cannot delete another user's job - and returns the same 404 as a missing one rather than confirming it exists |
| **Cascade** | The scan's report row and, for a load test, its `load_tests` row go with it, via ORM `delete-orphan`. No migration needed - it works against databases created before this fork |
| **Safety** | Only terminal jobs (complete / failed / cancelled) may be deleted. A queued / running / analysing / awaiting-decision job still has Celery tasks writing to its row; a genuinely hung one is reaped to `failed` first and then becomes deletable |
| **Partial success** | Bulk delete evaluates each id on its own and reports exactly what it kept and why - one running job in a selection doesn't block the other nineteen |
| **UI** | Delete in the ledger's selection bar, behind an inline confirm that states the count and warns it is irreversible |

Covered by [`backend/tests/test_scan_delete.py`](backend/tests/test_scan_delete.py)
(20 tests).

### 4. One performance score, computed once

The load-test score was being computed in two places. The orchestrator ran
`compute_performance_score` and stored the result, but `LoadTestResultsResponse`
never exposed it - so the frontend reimplemented the formula, and because the
browser is never sent the configured thresholds (15% of the score), its copy
hardcoded that component to a neutral 50. Every run with a latency or error
budget therefore displayed a number the backend never produced.

The stored score is now returned as `performance_score` and the client copy is
gone. The gauge also distinguishes "no score" from "scored 0" - a run that
failed before producing metrics renders `--`, not a claim that the target scored
the worst possible result. Pinned by
[`backend/tests/test_load_analyzer.py`](backend/tests/test_load_analyzer.py)
(16 tests, the first coverage the load-test pipeline has had).

### 5. Ledger and navigation fixes

- **Load tests are now distinguishable in the Scans ledger.** They already
  shared the `scans` table (`scan_type='loadtest'`), but the listing never
  exposed `scan_type` - so every row, load test included, linked to
  `/scan/{id}/status` and `/scan/{id}/report`, which a load test has no data
  for. Load-test rows now carry a gauge marker and link to
  `/loadtest/{id}/status`.
- **Removed the dead "Scan Status" rail item.** It hardlinked to
  `/scan/demo/status` - the status page for a scan literally named `demo` that
  nothing ever creates - so it always landed on "Connection lost - retrying…".
  A status page is inherently per-job, and every job already has a Status link
  on its ledger row.
- **Rail relabelled**: "New Scan" → "VAPT Scan", now that a scan is not the only
  kind of job. Wordmark reads ONUS-V2.

### 6. Operational changes

- **Backend published on host port `8001`** (container port is still 8000), so
  ONUS can run beside something else already holding 8000.
- **ZAP sidecar** runs as `root` with the `client`, `spiderAjax` and `domxss`
  add-ons uninstalled - they were the cause of the sidecar's slowest, least
  useful passes on this setup.

### Not done yet

Stated plainly so nobody plans around it:

- **No unified cross-pipeline report.** A load test and a scan still produce
  separate artefacts; there is no combined scan+load job type.
- **`loadtest-results.tsx` has only had a partial design-system pass.** The
  score gauge now uses the severity tokens, but the rest of the page still has
  raw Tailwind colours and a locally redefined `StatusPill` shadowing the
  shared one.
- **A single threshold breach is invisible in the performance score.** The
  threshold component starts at 100 and each breach costs 50, while *no*
  thresholds scores a neutral 50 - so breaching one budget lands on exactly the
  same value as never having set one. `thresholds_passed` on the results payload
  is the unambiguous signal; the score alone is not. Pinned by
  [`test_load_analyzer.py`](backend/tests/test_load_analyzer.py) so the
  behaviour is documented rather than surprising.

## Features

Inherited from upstream:

- **8 parallel scanning modules** (Celery) - network recon
  (ports/services/subdomains/DNS/WHOIS), web app scanning (ZAP + Nikto +
  Katana), SSL/TLS config, HTTP security headers, OWASP Top 10 checks, tech
  fingerprinting/WAF detection, CVE scanning (Nuclei), directory enumeration
  (FFUF).
- **Deterministic CVSS v3.1 scoring** - severity, CVSS score/vector, priority,
  and OWASP category are computed from a rule catalogue, never guessed by an
  LLM. Two runs of the same scan produce byte-identical numeric fields.
- **Confidence verification** - findings are passively re-checked
  (non-destructive re-observation only) and tagged confirmed / probable /
  unverified rather than silently dropped.
- **Optional local AI analysis** - Ollama + Qwen 2.5 7B turns scored findings
  into plain-English descriptions and remediation steps. Fully air-gapped; the
  tool works without it.
- **Context-aware remediation** - every finding ends with a concrete next step,
  and managed-platform detection (Vercel / Cloudflare / Netlify / GitHub Pages)
  means a platform-owned TLS finding says who controls that layer instead of
  giving impossible "edit your server config" advice.
- **PDF report + web dashboard** - WeasyPrint-rendered report and a Next.js
  dashboard, both driven by the same scored/described findings.

Added by this fork:

- **k6 load testing** - five scenarios, deterministic breaking-point detection
  and performance scoring, optional AI executive summary, live per-second
  charting. See [What's different from upstream](#whats-different-from-upstream).

## Architecture

Two pipelines, one queue, one job model.

```
VAPT scan
  domain → [recon | webscan | ssl_tls | headers | owasp | tech_fingerprint | nuclei | enumeration] (parallel, Celery)
         → any module failed/timed out? → pause for operator retry/continue/cancel
         → aggregator (dedup + OWASP-map + sort)
         → confidence verification (passive re-observation)
         → deterministic CVSS scoring
         → Ollama (Qwen 2.5 7B) prose
         → WeasyPrint PDF + PostgreSQL → dashboard / PDF download

Load test  (this fork)
  url + scenario → k6 (single Celery task, no chord, no decision pause)
         → deterministic metrics: breaking point + performance score
         → Ollama (Qwen 2.5 7B) executive summary + recommendations
         → PostgreSQL → live dashboard
```

<img src="docs/screenshots/architecture.png" alt="Six-layer architecture diagram" width="420">

Six layers: Next.js frontend → FastAPI → Celery/Redis → scanning modules or k6 →
Ollama (Qwen 2.5 7B) → WeasyPrint PDF + dashboard. Full details in
[`ARCHITECTURE.md`](ARCHITECTURE.md) (schemas, contracts, guardrails) and
[`docs/QUICK_REF.md`](docs/QUICK_REF.md).

## Prerequisites

- Docker + Docker Compose v2
- **~8GB free disk.** The built images total ~6.8GB (backend and worker are
  ~3.25GB each - they bundle Nuclei templates, a headless Chromium via
  Playwright, and the k6 binary - plus a ~270MB frontend), and the build itself
  needs headroom on top.
- **~6GB free RAM.** The ZAP sidecar alone is capped at 4GB (`mem_limit: 4g`),
  and Postgres, Redis, the API, the worker and the frontend run alongside it.
- First build takes roughly 10-15 minutes on a decent connection.

## Quick start

```bash
cp .env.example .env
cp backend/subfinder-config/provider-config.yaml.example backend/subfinder-config/provider-config.yaml
docker compose up -d
docker compose ps        # wait for zap to report healthy (~2 min)
```

- Dashboard: **http://localhost:3000**
- API + Swagger docs: **http://localhost:8001/docs** *(upstream publishes the
  backend on 8000; this fork moved it to 8001)*

Enter a domain, tick the authorization box, and start a scan - or go to
**Load Test** in the sidebar for the k6 pipeline.

**No sign-in, sign-up, or email verification.** Self-hosted ONUS is
single-operator by default.

**This works with no Ollama install.** CVSS/severity/priority scoring and load
test scoring are always deterministic - without Ollama running, results just get
a rule-based description template instead of AI-generated prose.

**Zero API keys are required.** Every tool it wraps (nmap, ZAP, Nikto,
testssl.sh, Nuclei, Amass, Naabu, httpx, WhatWeb, WAFW00F, FFUF, k6) and Ollama
itself work with no key at all. The subfinder config copy above is the one
optional exception - leaving it as the empty template is fine. To deepen
subdomain enumeration you can add two free-tier keys (a GitHub PAT and a
[ProjectDiscovery Chaos](https://chaos.projectdiscovery.io) key); see the
comments inside `provider-config.yaml.example`.

## Optional: enable AI-generated descriptions

Ollama runs **natively on the host** (not in Docker) so it can use the host's
GPU directly; containers reach it via `host.docker.internal`.

1. Install Ollama on the host: https://ollama.com/install.sh
2. Pull the model: `ollama pull qwen2.5:7b`
3. **Make Ollama reachable from Docker containers** (it defaults to
   `127.0.0.1`-only, which Docker's bridge network cannot reach):
   ```bash
   sudo systemctl edit ollama
   ```
   Add under `[Service]`:
   ```ini
   [Service]
   Environment="OLLAMA_HOST=0.0.0.0:11434"
   ```
   Then:
   ```bash
   sudo systemctl daemon-reload && sudo systemctl restart ollama
   ```
   Note: this makes Ollama reachable from your local network, not just Docker -
   fine on a personal machine, worth a firewall rule on a shared one.
4. Verify: `curl http://localhost:11434/api/tags`
5. Restart so the services pick it up: `docker compose restart backend worker`

## Optional: practice targets

The compose file defines 12 intentionally-vulnerable practice apps (Juice Shop,
DVWA, bWAPP, Mutillidae, NodeGoat, DVWP/WordPress behind a ModSecurity WAF,
Metasploitable2, WebGoat) for trying the scanner - and the load tester - against
something without needing your own authorized target. They're gated behind a
Compose profile so they never build/start by default:

```bash
docker compose --profile targets up -d
```

**Warning: these are intentionally-vulnerable, some genuinely backdoored,
services** (Metasploitable2 ships a live vsftpd backdoor). Only run the `targets`
profile on a machine that isn't reachable from the internet or a shared network -
never on a public cloud instance or an exposed host.

Two - `nodegoat` and `dvwp-wordpress` - build from source that isn't vendored
into this repo and must be cloned first:

```bash
git clone https://github.com/OWASP/NodeGoat nodegoat-src
git clone https://github.com/vavkamil/dvwp dvwp-src
```

Published ports: Juice Shop `:3001`, DVWA `:8081`, bWAPP `:8083`, Mutillidae
`:8084`, NodeGoat `:8085`, DVWP (via WAF, TLS) `:8444`, WebGoat `:8082`.
Metasploitable2 publishes no host port (reachable only from `backend`/`worker`
over Docker's internal network) since it exposes real backdoored network
services.

## Configuration

Env vars, set via `.env` (copied from `.env.example`):

| Variable | Default | Purpose |
|---|---|---|
| `POSTGRES_PASSWORD` | `vapt_secure_2025` | Database password |
| `SECRET_KEY` | `change_me_to_a_long_random_string` | Backend secret key |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | FastAPI allowed hosts |
| `OLLAMA_URL` | `http://host.docker.internal:11434` | Where the backend/worker reach Ollama |
| `SCAN_TIMEOUT_MULTIPLIER` | `1.5` | Scales every module's tool/Celery timeout - including the k6 subprocess. Drop to `1.0` for lab-tuned timings |
| `MAX_CONCURRENT_SCANS` | `3` | Concurrent-job cap (resource-exhaustion / target-politeness guard, also sizes the DB connection pool) |
| `ONUS_ENV` | `development` | `development` (localhost - weak secrets only warn) or `production` (weak `SECRET_KEY`/Postgres password become a hard boot failure) |

**The `POSTGRES_PASSWORD`/`SECRET_KEY` defaults are demo-only** - fine for a
local instance, but change both before deploying anywhere reachable by anyone
else. This is *enforced*: set `ONUS_ENV=production` and the backend refuses to
start while either is still a placeholder. Generate a strong key with
`python -c "import secrets; print(secrets.token_urlsafe(48))"`.

**Hosted-only features are off by default.** `REQUIRE_AUTH` (accounts / OAuth)
and `HOSTED_QUEUE_ENABLED` (scan queue) both default to `false` and aren't set in
`docker-compose.yml`. This fork is self-hosted only and leaves them off.

## Analytics (optional)

No analytics by default - nothing loads and no data leaves the browser. To
collect anonymous usage metrics on your own deployment, set a GA4 Measurement ID:

```bash
NEXT_PUBLIC_GA_ID=G-XXXXXXXXXX
```

It's a frontend build-time variable. When set, GA loads **only in production
builds** and tracks page views plus a few product events. Only anonymous,
low-cardinality events are sent - never scanned domains, load-test targets,
results, findings, report contents, or any personal data.

## Authorized use only

Scanning or load testing a target without explicit written authorization is
illegal under the Computer Misuse Act (UK), the CFAA (US), the IT Act 2000
(India), and equivalent statutes elsewhere. **A load test is not a gentler
request than a scan** - it deliberately generates sustained traffic and can
degrade or take down a service, which puts it closer to a denial-of-service
event than to a port scan in the eyes of most laws and most hosting providers.
Get written permission, agree a maintenance window, and tell the target's
operator before you start.

Both pipelines require authorization confirmation on every job and log the
operator + timestamp for accountability.
